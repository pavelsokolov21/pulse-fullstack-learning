# Roadmap: FullStack (Next.js + FastAPI)

Oct 5, 2026 · @Pavel

## Как пользоваться планом

План рассчитан на 8 часов в неделю и занимает около 32 недель (7-8 месяцев с учётом пропусков). Если часов будет больше, фазы просто закончатся раньше: порядок и критерии готовности не меняются.

| Фаза                             | Недель | Итог                                                          |
| -------------------------------- | ------ | ------------------------------------------------------------- |
| 0. Python для TS-разработчика    | 3      | CLI-утилита с async, типами и тестами                         |
| 1. FastAPI и авторизация         | 5      | API с ролями, фронт ходит через сгенерированный клиент        |
| 2. Базы данных                   | 7      | Схема на 1M+ строк и замеры оптимизации и безопасные миграции |
| 3. Архитектура и фоновые задачи  | 5      | Импорт CSV на 100k строк через очередь                        |
| 4. Инфраструктура и эксплуатация | 4      | Живой деплой, дашборд и алерт                                 |
| 5. Капстоун                      | 8      | B2B-сервис с табличным интерфейсом                            |

Тестирование идёт параллельно с фазами 1-4 и отдельных недель не занимает.

**Недельный ритм (8 часов):**

- 2 часа теории: документация, статья или курс по теме недели
- 5 часов практики: код в репозитории, а не конспект
- 1 час на заметку: что узнал, что не получилось, что вынесу на следующую неделю

**Правила:**

- Неделя закрыта, когда отмечены все пункты практики. Теория без практики не считается.
- Фаза закрыта только по критерию готовности, а не по числу прошедших недель. Не успел за отведённое время — продолжай ту же фазу, пока критерий не выполнен.
- Если тема уже знакома, пройди пункт по диагонали и поставь отметку: план не должен тормозить на известном.
- Весь код складывай в один репозиторий на фазу (или в один монорепозиторий), чтобы из них потом собрался портфолио.

## Сквозной проект: Pulse

Все фазы 0-4 проходим на одном проекте, **Pulse**: мини-монитор доступности сайтов (в духе Uptime Kuma). Он растёт вместе с тобой, а капстоун (фаза 5) остаётся отдельным проектом.

**Сущности:** `Monitor` (URL, интервал, владелец), `Check` (результат проверки: статус, `latency_ms`, срок SSL, время), `Incident` (серия неудачных проверок), `User` с ролями.

| Фаза | Что получает Pulse                                                                                                                                                                      |
| ---- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 0    | CLI проверяет список URL асинхронно: статус, время ответа, срок SSL. Утилиты недели 1: разбор интервалов (`5m`, `1h`), перцентиль p95, нормализация URL, определение «дребезга» статуса |
| 1    | API: пользователи, роли, CRUD мониторов, защита по ролям. Мини-фронт на Next.js через сгенерированный клиент                                                                            |
| 2    | PostgreSQL: история проверок на 1M+ строк, аптайм и p95 по окнам, индексы, миграции, Redis для текущего статуса                                                                         |
| 3    | Воркер по расписанию, импорт мониторов из CSV, статус в реальном времени через SSE, экспорт отчёта в S3-хранилище                                                                       |
| 4    | Docker, CI/CD, деплой, метрики и алерты. Pulse может мониторить сам себя и твой капстоун                                                                                                |

**Как читать практику в плане:** везде, где написано «поставщики», «заказы», «остаток товара» или «B2B-домен», берём сущности Pulse: мониторы, проверки, счётчик инцидентов. Например, гонка в неделе 5 фазы 2 воспроизводится на счётчике инцидентов, а N+1 на списке мониторов с последними проверками.

**Как набрать 1M+ строк:** 50 мониторов раз в минуту дают миллион проверок примерно за 14 дней. Не ждём: пишем сид-скрипт, который генерирует историю задним числом.

### Неделя 7. Миграции в проде

До этой недели миграции были «создал и применил на пустой базе». Теперь делаем то, что реально происходит на боевых данных: меняем схему таблицы в 1M+ строк так, чтобы не остановить работу сервиса.

**Теория (2 ч)**

- [ ] Alembic: цепочка ревизий, `upgrade` / `downgrade`, ветки и слияние (`heads`, `merge`), что автогенерация не видит (переименования, `enum`, серверные значения по умолчанию)
- [ ] Блокировки DDL в PostgreSQL: что блокирует `ALTER TABLE`, `lock_timeout`, `CREATE INDEX CONCURRENTLY`, DDL внутри транзакции
- [ ] Паттерн expand → migrate → contract для изменений без простоя

**Практика (5 ч)**

- [ ] Добавить колонку `NOT NULL` на таблицу заказов в 1M+ строк. Сначала с `DEFAULT`, затем `SET NOT NULL`; понять, где идёт полный скан таблицы, и обойти его через `CHECK ... NOT VALID` и `VALIDATE CONSTRAINT`
- [ ] Воспроизвести блокировку: в одной сессии `psql` держать открытую транзакцию, в другой запустить `ALTER TABLE`, посмотреть очередь в `pg_stat_activity` и `pg_locks`; затем повторить с `lock_timeout`
- [ ] Переименовать колонку без простоя за три миграции: добавить новую, перенести данные, удалить старую после переключения кода
- [ ] Создать индекс обычным способом и через `CREATE INDEX CONCURRENTLY` (в Alembic через `autocommit_block`), сравнить блокировки и время
- [ ] Data-миграция: заполнить новую колонку батчами по 10 тыс. строк с коммитом после каждой пачки
- [ ] Написать `downgrade` для каждой миграции и проверить откат на копии базы; сломать миграцию на середине и посмотреть, что откатилось (DDL в PostgreSQL транзакционный)
- [ ] Добавить в CI проверку: накатить все миграции на пустую базу и выполнить `alembic check`, чтобы схема совпадала с моделями

**Заметка (1 ч)**

- [ ] Чек-лист безопасной миграции: что проверяю до выката, чем рискую и как откатываюсь

### Критерий готовности

- [ ] Схема B2B-домена на 1M+ строк, миграции применяются с нуля одной командой
