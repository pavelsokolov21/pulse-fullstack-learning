# Pulse: backend

Монитор доступности сайтов. Сейчас это CLI: читает список мониторов из TOML-файла, асинхронно проверяет URL и печатает таблицу или JSON.

## Запуск

Нужны Python 3.12+ и [uv](https://docs.astral.sh/uv/). Команды выполняются из `backend/`.

```bash
uv sync                                   # установить зависимости
uv run pulse check monitors.toml          # таблица
uv run pulse check monitors.toml --json   # JSON
uv run pulse --help
```

Пример вывода:

```
STATUS  CODE  MS    URL                      ERROR
OK      200   112   https://example.com
FAIL    -     3000  https://down.example     Network Error: ConnectError
```

Код выхода: `0` все сайты доступны, `1` есть недоступные, `2` ошибка конфигурации (файл, TOML, поля монитора, `PULSE_*`). Это удобно для скриптов и CI.

## Файл мониторов

```toml
[[monitors]]
url = "example.com"   # схема https:// добавится сама
interval = "5m"       # число и единица: s, m, h
timeout = 10          # секунды, необязательно (по умолчанию 10)
```

Неизвестные ключи и неверные значения это ошибка: файл не применяется частично.

## Настройки через окружение

| Переменная          | По умолчанию | Смысл                                | Ограничение |
| ------------------- | ------------ | ------------------------------------ | ----------- |
| `PULSE_CONCURRENCY` | `10`         | сколько проверок идёт одновременно   | целое, >= 1 |
| `PULSE_RETRIES`     | `2`          | число повторов после сетевого сбоя   | целое, >= 0 |
| `PULSE_RETRY_DELAY` | `0.5`        | пауза между повторами, секунды       | число, >= 0 |

```bash
PULSE_CONCURRENCY=50 PULSE_RETRIES=0 uv run pulse check monitors.toml
```

Повторяются только сетевые сбои (таймаут, отказ соединения, DNS). Ответ сервера, даже 503, считается результатом проверки и не повторяется.

## Проверки качества

```bash
uv run poe check    # ruff + pyright (strict) + pytest
```

По отдельности: `uv run poe lint`, `uv run poe types`, `uv run poe test`, `uv run poe watch` (тесты при изменении файлов).

### Тесты и база

Тесты репозиториев, сервисов и API идут в настоящий PostgreSQL: ограничения схемы, права ролей и гонки нельзя проверить на подделке. Нужны запущенные PostgreSQL и Redis (`docker compose up -d`) и корневой `.env` (`cp .env.example .env`): из него тесты берут логин и пароль суперпользователя и пароль Redis. Иначе задайте `PULSE_TEST_DATABASE_URL=postgresql+psycopg://ЛОГИН:ПАРОЛЬ@127.0.0.1:5432/pulse_test` и `PULSE_TEST_REDIS_URL=redis://:ПАРОЛЬ@127.0.0.1:6379/15`. Redis-тесты работают в базе №15 и стирают её (`FLUSHDB`): номер 0 запрещён.

Что делают тесты сами: создают базу `pulse_test` (имя обязано кончаться на `_test`, в ней стирают данные), применяют миграции Alembic (`alembic upgrade head`, как в бою) и пересоздают схему, когда изменился `schema.sql` или файл миграции. Приложение в тестах подключается ролью `pulse_app`, поэтому права из схемы действуют и там (например, `UPDATE checks` запрещён).

- **Репозитории и сервисы:** каждый тест идёт в транзакции, которая откатывается в конце (`session` в `tests/conftest.py`). Идентификаторы после отката не возвращаются: не ждите конкретных id.
- **API:** `TestClient` запускает приложение в своём потоке и event loop, делить с ним одну транзакцию нельзя. Поэтому перед каждым тестом и после него таблицы очищаются (`TRUNCATE ... RESTART IDENTITY`), и нумерация id снова с 1.
- **Гонки** (`tests/services/test_concurrency.py`): отдельные соединения и настоящие коммиты.

## Структура

Слои зависят только вниз: `api → services → repositories → domain`. `core` не зависит ни от кого, `checks` и `cli` стоят сбоку. Направление импортов проверяет `tests/test_architecture.py`.

```
src/pulse/
  api/            HTTP: сборка приложения, ошибки, Depends, cookie
    middlewares/  ASGI-middleware (request-id)
    routers/      обработчики эндпоинтов
    schemas/      тела запросов и ответов (Create / Update / Read)
  services/       операции над мониторами, бизнес-правила
  repositories/   хранение: SQLAlchemy 2.0 (async) и PostgreSQL; ORM-модели не выходят за этот слой
  domain/         сущности, общие типы с валидацией, доменные ошибки
  checks/         проверка URL: runner, скользящее окно, статистика
  cli/            команда `pulse check`, загрузка мониторов из TOML
  core/           настройки, утилиты, декораторы, контекст запроса для логов
tests/            зеркалит структуру src/pulse/
```

Запуск API: нужны секрет подписи JWT, адрес базы и адрес Redis (без них приложение не стартует, а Redis проверяется командой PING при запуске). Схему базы сначала нужно создать, см. «Схему БД» ниже. Приложение ходит в базу ролью `pulse_app` (не суперпользователем), пароль тот, что вы передали в `roles.sql`.

Значения лежат в `backend/.env.dev` (он в `.gitignore`, шаблон без секретов: [.env.example](.env.example)). Один раз: `cp .env.example .env.dev` и подставьте свои значения. Дальше запуск одной командой, задача `dev` сама читает файл и добавляет `--no-proxy-headers`:

```bash
uv run poe dev                                         # http://127.0.0.1:8000/docs
```

## Схема БД (PostgreSQL)

Файлы в [db/](db/): [roles.sql](db/roles.sql) (роли), [schema.sql](db/schema.sql) (базовый DDL, применяется первой миграцией Alembic: `users`, `refresh_tokens`, `monitors`, `checks`, `incidents`, `channels`, `monitor_channels`, `audit_log`) и [constraints_test.sql](db/constraints_test.sql) (по тесту на каждое ограничение и право, всё в транзакции с откатом). Правила записаны в самой схеме (NOT NULL, UNIQUE, CHECK, внешние ключи с явным `ON DELETE`, `EXCLUDE`), у каждого ограничения есть имя.

Логин и пароль суперпользователя Postgres хранятся не в репозитории, а в `.env` в корне (он в `.gitignore`). Перед первым запуском: `cp .env.example .env` и задайте `POSTGRES_PASSWORD`. Без него `docker compose` не стартует. В командах ниже `-U pulse` это значение `POSTGRES_USER`. Postgres применяет эти значения только при создании тома `pgdata`: смена пароля в `.env` для существующей базы ничего не меняет (для этого `ALTER ROLE`, либо `docker compose down -v` с потерей данных).

Применять нужно в отдельную базу: в `seed.sql` из корня репозитория (учебные запросы) тоже есть таблицы `monitors` и `checks`, и они бы столкнулись. Порядок важен: роли, база с владельцем `pulse_migrator`, миграции от его имени, проверки суперпользователем.

```bash
docker compose up -d db
docker compose exec -T db psql -U pulse -d postgres -v ON_ERROR_STOP=1 \
  -v migrator_password=migrator -v app_password=app < db/roles.sql
docker compose exec -T db psql -U pulse -d postgres -c 'CREATE DATABASE pulse_schema OWNER pulse_migrator'
PULSE_MIGRATE_DATABASE_URL='postgresql+psycopg://pulse_migrator:migrator@127.0.0.1:5432/pulse_schema' \
  uv run alembic upgrade head
docker compose exec -T db psql -U pulse -d pulse_schema -v ON_ERROR_STOP=1 < db/constraints_test.sql
# ... 150 проверок пройдено
```

Ключевые решения:

- **Две роли.** `pulse_migrator` владеет схемой и нужен только миграциям. Приложение подключается как `pulse_app`: ничем не владеет, DDL ему недоступен. Права выданы по таблицам, а не «всё». На `audit_log` у приложения только `INSERT` и `SELECT`, поэтому журнал нельзя переписать или очистить даже из взломанного приложения. На `checks` нет `UPDATE`: результаты проверок не правят. Пароли передаются переменными psql, в репозиторий не попадают.
- **`ON DELETE`.** Токены, каналы и проверки удаляются каскадом вместе с владельцем (`users` → токены, каналы; `monitors` → проверки, инциденты, подписки). Пользователя с мониторами удалить нельзя (`RESTRICT`): одной командой история не пропадёт. Журнал и инциденты переживают удаление (`SET NULL`).
- **Владение на уровне данных.** `monitor_channels` хранит `owner_id` и ссылается на `monitors` и `channels` составными ключами `(id, owner_id)`: БД не даст подписать чужой канал на свой монитор. Так же `incidents` ссылаются на проверки составным ключом `(id, monitor_id)`: инцидент не может указывать на проверку чужого монитора. `ON DELETE SET NULL (столбец)` (PG 15+) обнуляет только ссылку на проверку, а `monitor_id` остаётся.
- **Интервал и таймаут.** Интервал хранится целыми секундами (`interval_seconds`), а не типом `interval`: у него есть месяцы и дни без фиксированной длины. Границы 30 секунд и 24 часа, таймаут строго короче интервала, иначе проверки монитора накладываются друг на друга. Те же правила проверяют Pydantic (`domain/types.py`, `domain/monitors.py`) и сервис, так что приложение и БД не расходятся. Представление везде одно: в JSON секунды, в домене `timedelta`, в БД integer; преобразование только на границе репозитория.
- **Роль без значения по умолчанию.** `users.role NOT NULL` без `DEFAULT`: забытое поле не выдаст права молча. Роль задаёт сервис (регистрация создаёт `manager`), `UserRepository.create` тоже требует её явно.
- **Инциденты.** `EXCLUDE USING gist` запрещает пересечение инцидентов монитора, в том числе второй открытый (нужно расширение `btree_gist`, оно уже в образе `postgres`).
- **`checks.ok`** вычисляется из `status_code` (столбец `GENERATED ... STORED`), поэтому не может разойтись с ним.
- **Индексы** только под ограничения, внешние ключи и запрос «последние проверки монитора». Остальные после `EXPLAIN ANALYZE` на данных. Составной ключ инцидентов требует `UNIQUE (id, monitor_id)` на `checks`: это ещё один индекс на самой большой таблице.

### Миграции (Alembic)

Схему меняют только миграции; приложение их не запускает. Выполняет их роль `pulse_migrator` (владелец таблиц), поэтому адрес берётся из отдельной переменной `PULSE_MIGRATE_DATABASE_URL` (в нём пароль, в репозиторий не кладите). Файлы: [alembic.ini](alembic.ini), [migrations/env.py](migrations/env.py), [migrations/versions/](migrations/versions/).

Адрес можно положить в `backend/.env.migrate` (строка `PULSE_MIGRATE_DATABASE_URL=...`, файл в `.gitignore`, приложение его не читает). Тогда `uv run poe migrate` применяет всё без экспорта переменной, а `uv run poe check-migrations` прогоняет проверку «пустая база → `upgrade head` → `alembic check` → откат и накат» на временной базе.

```bash
export PULSE_MIGRATE_DATABASE_URL='postgresql+psycopg://pulse_migrator:ПАРОЛЬ@127.0.0.1:5432/pulse_schema'
uv run alembic upgrade head              # применить всё
uv run alembic upgrade head --sql        # только напечатать SQL, базу не трогать
uv run alembic current                   # какая версия сейчас в базе
uv run alembic history                   # список миграций
uv run alembic downgrade -1              # откатить последнюю
uv run alembic revision --autogenerate --rev-id 0002 -m "add foo"   # новая по моделям
uv run alembic check                     # модели и база совпадают? (падает при расхождении)
```

Как работать:

- **Правка модели → миграция.** Изменили `repositories/models.py`, сгенерировали `revision --autogenerate`, **прочитали** сгенерированный файл и поправили руками: автогенерация не видит CHECK, не отличает переименование от «удалить и создать», не знает про данные. Для таблицы с данными в бою нужна безопасная последовательность (добавить столбец допускающим NULL, заполнить, потом `NOT NULL`).
- **`alembic check`** в тестах (`tests/migrations`) падает, если модели ORM разошлись с миграциями: забыли миграцию или забыли модель.
- **Не описаны моделями** `incidents`, `channels`, `monitor_channels`, `audit_log`: приложение их пока не использует, автогенерация их игнорирует (`include_object` в `env.py`). Добавите модель, и они попадут под сравнение.
- **Базовая миграция** `0001` применяет `db/schema.sql` как есть, потому что в нём комментарии о каждом решении и вещи, которые автогенерация не умеет: `EXCLUDE`, `GENERATED`, `GRANT`, составные ключи с `ON DELETE SET NULL (столбец)`. Файл после выпуска миграции не правят.
- **Откат** `0001` удаляет таблицы, но не расширение `btree_gist` и не роли: они общие.

### Миграции на живых данных (неделя 7)

Опыты идут на копии `pulse_lab` (1M+ строк в `checks`), рабочая `pulse_schema` не трогается. Всё лежит в [db/lab/](db/lab/):

```bash
db/lab/lab.sh reset                        # pulse_lab = CREATE DATABASE ... TEMPLATE pulse_schema (секунды)
db/lab/lab.sh psql db/lab/02_not_null_safe.sql
export PULSE_LAB_URL='postgresql://pulse_app:ПАРОЛЬ@127.0.0.1:5432/pulse_lab'
uv run python db/lab/loader.py --rate 200  # нагрузчик: INSERT + чтение последних проверок, раз в секунду max задержки
uv run python db/lab/lock_demo.py          # очередь блокировок в pg_stat_activity и pg_locks
```

Без нагрузчика блокировку не видно: он печатает по секундам максимум задержки, и «застрявшая» секунда видна сразу. Базовая линия: 190 циклов/с, медиана 1.5 мс, максимум до 20 мс.

**Миграции** (все нагрузочно проверены на копии, у каждой есть `downgrade`, тесты в [tests/migrations/test_live_data_migrations.py](tests/migrations/test_live_data_migrations.py)):

| Ревизия | Что | Приём |
| --- | --- | --- |
| 0003 | `checks.region text NOT NULL` | `ADD COLUMN ... DEFAULT 'eu'` (мгновенно) → `CHECK ... NOT VALID` → `VALIDATE CONSTRAINT` → `SET NOT NULL` → снять CHECK |
| 0004 | индекс `checks(checked_at)` | `CREATE INDEX CONCURRENTLY` в `autocommit_block` |
| 0005-0007 | `latency_ms` → `duration_ms` | expand (колонка + триггер-синхронизация) → migrate (батчи по 10 тыс., коммит после каждой) → contract (NOT NULL, снять триггер и старую колонку) |

**Замеры** (PostgreSQL 18, 1 000 060 строк, таблица 99 МБ, всё в кеше; цифры как есть, без округления в пользу вывода):

| Что | Время | Что видел нагрузчик |
| --- | --- | --- |
| `ADD COLUMN ... DEFAULT 'eu'` (константа) | 0.35-0.9 мс | ничего |
| `ADD COLUMN ... DEFAULT clock_timestamp()` (волатильный) | 1417 мс, таблица переписана | под ACCESS EXCLUSIVE, не гонялся с нагрузчиком, откатил |
| `SET NOT NULL` в лоб | 62 мс под ACCESS EXCLUSIVE, сервер пишет `verifying table "checks"` | max 54.6 мс против 5-8 в норме |
| `NOT VALID` → `VALIDATE` → `SET NOT NULL` | 0.7 мс + 48.5 мс (SHARE UPDATE EXCLUSIVE) + скан пропущен | max 7.8 мс, без всплесков |
| `CREATE INDEX` обычный | 204 мс, на это время INSERT стоят | max вставки 187 мс (4 запроса > 100 мс), чтение не страдает |
| `CREATE INDEX CONCURRENTLY` | 321 мс (в 1.6 раза дольше) | max вставки 15.9 мс, без всплесков |
| Бэкфилл `duration_ms`, батчи по 10 тыс. | 22.8 с на 1 млн строк, оба вида кода пишут параллельно | p99 вставки 16 мс (в норме 6), один всплеск 216 мс; ошибок и несовпадений 0 |
| `downgrade` шага 0007 (копия обратно) | 21.6 с | данные совпали, 0 расхождений |

Очередь блокировок ([db/lab/lock_demo.py](db/lab/lock_demo.py)): сессия A держит открытую транзакцию с чтением `checks` (ACCESS SHARE), миграция B ждёт ACCESS EXCLUSIVE, а обычный SELECT приложения C встаёт **за B**, хотя A ему не мешает. Без `lock_timeout` нагрузчик замер на 3.0 с, с `lock_timeout = 1s` миграция упала с ошибкой через 1.01 с и остановка составила 1.0 с.

**Индекс по `checked_at`, `EXPLAIN (ANALYZE, BUFFERS)`, кеш прогрет:**

| Запрос | Было (индекс `monitor_id, checked_at`) | Полный скан (индексы запрещены) | Стало (+ `checked_at`) |
| --- | --- | --- | --- |
| последний час, 7 строк | 0.366 мс, 410 буферов | 41.9 мс, 12 605 | **0.050 мс, 7 буферов** |
| час посреди данных, 1347 строк | 0.611 мс, 522 | 40.4 мс | 0.701 мс, 531 (планировщик остался на старом индексе) |
| сутки, агрегат, 32 455 строк | 4.04 мс, 1178 | 42.0 мс | 3.68 мс, 630 |

Вывод: в PostgreSQL 18 составной индекс `(monitor_id, checked_at)` уже работает как *skip scan* по `monitor_id` (всего 132 значения), поэтому «долг недели 4» здесь проявляется мягче, чем на PG 17 и ниже. Новый индекс заметно выигрывает на самом частом запросе («последний час»: в 7 раз по времени, в 60 раз по буферам), на остальных почти нейтрален, стоит 21 МБ (+20% к индексам таблицы). Выгода растёт с числом мониторов: цена skip scan пропорциональна числу различных `monitor_id`, а здесь их 132 (эту зависимость я не измерял).

### Тестовые данные (Faker)

[db/seed.py](db/seed.py) заполняет все восемь таблиц правдоподобными данными: пользователи с ролями, сессии с цепочками токенов, каналы и мониторы (интервалы 30 с..1 ч), история проверок с отказами сериями, инциденты из этих серий (часть открыта), подписки каналов только на мониторы владельца и журнал аудита. Данные грузятся от имени `pulse_app` (заодно проверяются его права) одной транзакцией, поэтому всё, что не прошло ограничения схемы, откатывается целиком. Генерация в [db/seed_data.py](db/seed_data.py) не трогает БД, а `seed` и `now` делают результат воспроизводимым.

```bash
uv run python db/seed.py                      # в пустую базу pulse_schema
uv run python db/seed.py --reset              # очистить таблицы (от pulse_migrator) и загрузить заново
uv run python db/seed.py --users 100 --checks 500 --seed 7
```

По умолчанию загрузка идёт на `postgresql://pulse_app:app@localhost:5432/pulse_schema`, очистка на `...pulse_migrator:migrator@...`. Это учебные пароли локального Docker. Свои подключения задаются флагами `--dsn` и `--reset-dsn` или переменными `PULSE_SEED_DSN` и `PULSE_SEED_RESET_DSN` (флаг главнее). Скрипт стирает и добавляет данные, поэтому на нелокальный сервер без `--allow-remote` он не подключается, а в непустую базу без `--reset` не грузит. Пароль у всех пользователей `pulse-demo-password`, админ `admin@example.com`. Проверки генератора и загрузчика лежат в `tests/db/`.

### Данные для замеров (1M+ строк в `checks`)

[db/seed_bulk.py](db/seed_bulk.py) дополняет `checks` до `--target` строк (по умолчанию миллион) по уже загруженным мониторам (сначала `db/seed.py`). Строки генерирует сама база (`generate_series`): на миллион уходит около 10 секунд, в Python объекты не создаются. Повторный запуск ничего не добавляет, пока строк не меньше цели.

```bash
uv run python db/seed_bulk.py                         # до 1 000 000, окно 30 дней
```

Данные устроены как настоящие, чтобы планы запросов были правдоподобными: проверки размазаны по окну `--days`, частый монитор даёт больше строк (доля пропорциональна `1 / interval`), сбои идут сериями (простои), у успешных ответов задержка логнормальная (медиана около 55 мс). Вставка идёт от `pulse_app`, а `ANALYZE` и отчёт от `pulse_migrator`.

В конце скрипт печатает «Условия замеров» в Markdown: версию PostgreSQL, `shared_buffers`, `effective_cache_size`, `work_mem`, `random_page_cost`, размер таблицы и индексов `checks` и число строк по всем таблицам. Вставьте этот блок в заметку рядом с таблицей результатов: без него цифры нельзя сравнивать.

**Осторожно:** после каждой проверки приложение оставляет на монитор не больше `PULSE_API_MAX_CHECKS_PER_MONITOR` строк (по умолчанию 100) и удаляет остальные. Пока меряете, запускайте API с большим значением (например `100000000`) или не запускайте проверки через него, иначе нагрузочные данные сами сожмутся.

## API

Все ручки `/monitors/...` требуют заголовок `Authorization: Bearer <токен>`.

**Роли** отвечают на вопрос «какие действия разрешены», **владение** — «над какими объектами»:

| Роль      | Действия                                         | Объекты                |
| --------- | ------------------------------------------------ | ---------------------- |
| `admin`   | читать и менять                                  | любые мониторы         |
| `manager` | читать и менять                                  | только свои            |
| `viewer`  | только читать                                    | только свои            |

Роль без права на действие получает 403. Чужой монитор неотличим от несуществующего: 404 (так по ответу нельзя перебирать чужие id). Новый пользователь регистрируется менеджером; роль в запросе регистрации передать нельзя. URL монитора уникален в рамках владельца.

**Сессия.** Вход возвращает короткий access-токен (JWT) в теле ответа, а долгий refresh-токен кладёт в httpOnly-cookie `refresh_token` (путь `/auth` или `PULSE_API_REFRESH_COOKIE_PATH`, `SameSite=Strict`, в prod ещё `Secure`). Каждый `POST /auth/refresh` меняет refresh-токен на новый, а старый отзывает. Если приходит уже отозванный токен, отзывается вся цепочка: значит, им воспользовались дважды. Access-токен после выхода живёт до своего срока (до 15 минут): отозвать можно только refresh.

**Вход ограничен по частоте:** не больше 5 попыток с одного адреса за 60 секунд, дальше 429 с заголовком `Retry-After`. За прокси запускайте сервер с `--proxy-headers --forwarded-allow-ips=<адрес прокси>`: иначе все клиенты выглядят как один адрес.

| Метод и путь                     | Что делает                                      |
| -------------------------------- | ----------------------------------------------- |
| `POST /auth/register`            | регистрация: `{email, password}`, пароль 8–128 символов (201; 409, если email занят) |
| `POST /auth/login`               | вход по форме OAuth2 (`username` = email, `password`), выдаёт JWT (401 при ошибке) |
| `POST /auth/refresh`             | новая пара токенов по refresh-cookie (ротация); 401, если токен неизвестен, просрочен или уже использован |
| `POST /auth/logout`              | отзывает сессию и сбрасывает cookie (204, повторный вызов тоже 204) |
| `GET /auth/me`                   | текущий пользователь по токену                  |
| `POST /monitors`                 | создать монитор (201; 409, если URL уже есть; 422, если интервал вне 30 с..24 ч или таймаут не короче интервала) |
| `GET /monitors`                  | страница мониторов `{items, total, limit, offset}` с `owner_email` у каждого; `?limit=1..100` (по умолчанию 20), `?offset=0..`; админу все, остальным свои |
| `GET /monitors/{id}`             | один монитор (404, если нет)                    |
| `PATCH /monitors/{id}`           | изменить переданные поля                        |
| `DELETE /monitors/{id}`          | удалить монитор и его проверки (204)            |
| `POST /monitors/{id}/checks`     | проверить монитор сейчас (201)                  |
| `GET /monitors/{id}/checks`      | последние проверки, `?limit=1..100` (по умолчанию 20) |

Данные (в том числе пользователи и сессии) лежат в PostgreSQL и переживают перезапуск. Запрос работает в одной транзакции: она фиксируется, когда обработчик завершился успешно, и откатывается при любой ошибке. Все ошибки имеют вид `{"code": ..., "message": ...}`, а у каждого ответа есть заголовок `X-Request-ID`.

### Схема OpenAPI и клиент фронтенда

`operationId` в схеме равен имени обработчика (`create_monitor`, `list_checks`), а не `create_monitor_monitors_post`. Схему можно записать в файл, не запуская сервер:

```bash
uv run python -m pulse.api.export_openapi openapi.json
uv run poe openapi            # то же, в ../frontend/openapi.json
```

Типы для фронтенда обновляются одной командой `npm run gen:api` в `frontend/` (она сама вызывает экспорт). Тест `test_checked_in_frontend_schema_is_up_to_date` падает, если `frontend/openapi.json` отстал от API.

Фронтенд обращается к API через прокси Next.js (`rewrites`: `/api/*` уходит на FastAPI), поэтому origin один, CORS не нужен, а `SameSite=Strict` не мешает. Cookie с refresh при этом должна ходить на `/api/auth`, и сервер запускают так:

```bash
PULSE_API_REFRESH_COOKIE_PATH=/api/auth uv run poe dev   # уже стоит в .env.dev
```

Без этой переменной (путь `/auth`) refresh работает при прямых запросах к API, например из `/docs`.

**Адрес клиента за прокси.** `rewrites` в Next.js не ставит `X-Forwarded-For`, а пропускает заголовок клиента без изменений. Поэтому лимит на вход (он считается по адресу) зависит от способа запуска:

- **Локально:** запускайте сервер с `--no-proxy-headers` (`uv run fastapi dev --no-proxy-headers`). Иначе uvicorn доверяет заголовку от `127.0.0.1`, и клиент подменой `X-Forwarded-For` обходит лимит. Без доверия все запросы выглядят как адрес Next.js, то есть лимит общий: для разработки это нормально.
- **В prod:** перед Next.js должен стоять балансировщик, который **дописывает** настоящий адрес в `X-Forwarded-For` (nginx, облачный балансировщик). Сервер запускают с `--proxy-headers --forwarded-allow-ips=<адрес Next.js>`: uvicorn идёт по цепочке справа налево и берёт первый недоверенный адрес, то есть тот, что дописал балансировщик. Без балансировщика лимит по адресу не работает ни так, ни так.

### Настройки API

Читаются при создании приложения; неверное значение роняет запуск, а не первый запрос. Хост и порт задаёт запускающая команда: `uv run fastapi dev --host 0.0.0.0 --port 9000`.

| Переменная                        | По умолчанию | Смысл                                                   |
| --------------------------------- | ------------ | ------------------------------------------------------- |
| `PULSE_API_ENVIRONMENT`           | `dev`        | `dev` или `prod`; в `prod` отключены `/docs` и `/redoc` |
| `PULSE_API_LOG_LEVEL`             | `INFO`       | уровень логов `pulse.*`: DEBUG, INFO, WARNING, ERROR, CRITICAL |
| `PULSE_API_MAX_CHECKS_PER_MONITOR` | `100`       | сколько последних проверок хранить на монитор (>= 1)    |
| `PULSE_API_DATABASE_URL`          | обязательно  | адрес PostgreSQL ролью `pulse_app`: `postgresql+psycopg://логин:пароль@хост:порт/база` (содержит пароль, в репозиторий не кладите) |
| `PULSE_API_REDIS_URL`             | обязательно  | адрес Redis: `redis://:пароль@хост:порт/номер_базы` (содержит пароль). Кеш отчётов и лимит входа |
| `PULSE_API_REPORT_CACHE_TTL_SECONDS` | `60`      | сколько живёт кеш отчёта монитора; новая проверка сбрасывает его сразу |
| `PULSE_API_JWT_SECRET`            | обязательно  | ключ подписи JWT (HS256), не короче 32 символов         |
| `PULSE_API_ACCESS_TOKEN_TTL_MINUTES` | `15`      | срок жизни access-токена, минуты (>= 1)                 |
| `PULSE_API_REFRESH_TOKEN_TTL_DAYS` | `7`         | срок жизни refresh-токена, дни (>= 1)                   |
| `PULSE_API_LOGIN_RATE_LIMIT_ATTEMPTS` | `5`      | попыток входа с одного адреса за окно (>= 1)            |
| `PULSE_API_LOGIN_RATE_LIMIT_WINDOW_SECONDS` | `60` | окно ограничения входа, секунды (>= 1)                |
| `PULSE_API_REFRESH_COOKIE_PATH`   | `/auth`      | путь cookie с refresh-токеном; за прокси Next.js нужен `/api/auth` |

В `prod` схема `/openapi.json` остаётся доступной (по ней строится клиент фронтенда).

## Redis: кеш отчёта, лимит входа

Redis поднимается в `docker-compose.yml` (порт только на `127.0.0.1`, пароль обязателен, диск отключён: кеш и счётчики не нужно переживать перезапуск). Пароль `REDIS_PASSWORD` задаётся в корневом `.env` (образец в `.env.example`); без него `docker compose` не стартует. Один асинхронный клиент `redis.asyncio` создаётся на процесс в `lifespan` и закрывается при остановке.

- **Отчёт монитора** `GET /monitors/{id}/report?window=24h|7d|30d`: аптайм, среднее и p95 задержки (по проверкам с ответом). Cache-aside: промах считает по базе и кладёт в Redis на TTL, попадание базу за отчётом не трогает. Заголовок `X-Cache: HIT|MISS`. Новая проверка монитора сбрасывает кеш (счётчик версий монитора поднимается после коммита), так что отчёт сразу после проверки не устаревший. Права проверяются раньше кеша. Если Redis недоступен, отчёт считается по базе: кеш это оптимизация, а не источник данных. Замер: `uv run python db/bench_report_cache.py`.
- **Лимит входа** `RedisRateLimiter`: скользящее окно на sorted set, проверка и запись одним Lua-скриптом (неделимо), время берёт сам Redis. Лимит общий для всех процессов сервера. При недоступном Redis запросы пропускаются (fail open) с записью в лог.
- **Журнал аудита** `audit_log`: `monitor.create`, `monitor.update`, `monitor.delete` пишутся в одной транзакции с изменением (та же сессия, один коммит), с `request_id` запроса. У приложения нет `UPDATE` и `DELETE` на эту таблицу.
